## Automations

Found 2026-07-15, reproduced live: reorder "Team routing chatbot"'s buttons (e.g. move button 3 to position 2) while a visitor's already-sent bot_prompt_buttons message (old order) is still unclicked. The visitor then clicks the button that's visually still in the same place for them — and it executes the *new* button that now sits at that array position, not the one they saw/pressed (wrong team routing, wrong reply, wrong sub-menu, no error surfaced).

| # | Title | Description | Priority |
|---|-------|-------------|----------|
| AUT1 | **Resolve bot button clicks by stable ID, not array position** | Root cause: `handle_bot_button_click`/`_resolve_button_at_path` (`conversation_orchestrator.py`) resolve a click by walking `button_path` — a list of *array indices* — against the **live** `Automation.nodes` config at click time, not against the button set actually rendered to that visitor when the message was sent. Any edit to the buttons array between send and click (reorder, insert, delete) shifts indices, so the same position now points at a different button. Industry-standard fix — the same technique Slack Block Kit/Telegram inline keyboards/Stripe use for interactive-message callbacks: give every button, and every nested sub_prompt button recursively, a permanent random `id` minted once at creation time in the editor and never regenerated on edit (label/team/reply changes keep the same id — only "Add" mints a new one). Thread it through the whole path: `Automation.nodes[].config.buttons[].id` → the WS payload/stored message snapshot the widget renders → the widget sends the clicked button's id (an id-path, replacing today's index-path) back on click → backend resolves by **id match** against the live config, never by position. This makes reordering (and label/reply edits) a pure no-op for conversations already mid-flow — a button keeps its identity regardless of where it now sits in the array or what its text says. Edge case to design for explicitly: a button *deleted* after being shown — id lookup will legitimately fail, so it needs a graceful visitor-facing fallback ("This option is no longer available — please continue below" or similar) instead of a silent no-op or a 500. Work involved: (1) editor (`AutomationFlowCanvas.tsx`) — mint an id in the `Add` handler for both top-level and nested buttons; (2) one-time backward-compat handling for buttons already saved without an id (lazy-assign on next load/save, since no DB migration is needed — this is just a JSON field); (3) backend id-based resolution replacing index-based; (4) widget sends id-path instead of index-path. Worth a quick check whether this same "position/timing used as identity instead of a stable id" pattern shows up anywhere else in the codebase (raised alongside this bug) — not confirmed, just flagged for a look. | High |

## Visitor Contact Capture

| # | Title | Description | Priority |
|---|-------|-------------|----------|
| CC1 | **Structured contact capture during a live (online) chat** | Today, contact info only gets captured cleanly when all agents are offline (structured form → `conversations.visitor_name/visitor_email/visitor_phone`, shown in `VisitorDetailsPanel`). When agents are online they just ask in chat, and visitors reply in free text ("ragul7708196644, Ragul, 7708196644") that nothing parses — agents have to manually retype it into the panel's edit fields. Decided approach: **agent-triggered inline "contact card"** in the chat thread (same industry-standard pattern as Intercom/Drift/Crisp's "collect visitor info" step), not regex-parsing free text (unreliable for phone/name, and a wrong silent auto-fill is worse than an empty field). Reuses a lot of existing plumbing: the `visitor_contact` WS message type already fills only-empty `conversations.visitor_*` columns (backend/app/api/ws_chat.py); the `bot_prompt_buttons` message type already proves the "enriched JSON message content, decoded by `message_presenter.py`, rendered as a real interactive widget instead of a text bubble" pattern; the offline contact-overlay's form UI/validation (name/phone digit-stripping/email regex) can be reused as the card's rendering; the agent-side trigger fits naturally next to the existing `/shortcut` mechanism in `ChatComposer.tsx` (e.g. a `/contact` trigger or a composer icon). New work: a new `event_type` for the card message, the widget-side renderer (smaller sibling of `appendBotPromptWithButtons`), and the agent trigger UI. Optional low-cost follow-up: a passive, non-committal "detected phone/email in recent messages — apply?" suggestion chip in the visitor panel as a backstop for agents who skip the card — never silently auto-filled. | Medium |

## Security

Found 2026-07-06: an agent can copy a visitor's `session_id` (visible as a full, untruncated tooltip + searchable text in `CustomersVisitors.tsx`) into their own browser's `ai_chatassist_session_id_{websiteId}` localStorage key and gain full read/write access to that visitor's conversation. Root cause: `session_id` is used as both the public identifier *and* the sole bearer credential for a conversation — classic identifier/secret conflation.

**Fixed 2026-07-09** (commit `72bc834`): SEC1 (expanded in scope beyond the original write-up — `chat_ws_with_conversation` wasn't just missing the domain lock, its history-send was completely unconditional on session ownership, so anyone who knew `website_id` + a small sequential `conversation_id` could read the full transcript regardless of `session_id`; both the domain lock and an ownership gate are now in place), SEC2, SEC4, and the connect/read-rate-limiting half of SEC5. Verified via real (not just syntax-checked) tests: mismatched session → rejected before any data sent, matching session → still works normally. Remaining below.

| # | Title | Description | Priority |
|---|-------|-------------|----------|
| SEC3 | **Separate session identifier from session credential** | The actual structural fix. Generate a second random secret alongside `session_id` at first connect, store both in the widget's localStorage entry, and require *both* (not just session_id) to open a WS or read history. Never return the secret in any agent-facing API response. `session_id` is trusted as the sole credential across 2 WS routes and 5 REST routes today — a real fix means threading the secret through all of them at once, plus a soft-migration path so no currently-connected live visitor gets locked out (issue a secret transparently on first connect if one's missing, only start hard-rejecting once one has actually been issued). Real auth-model change — scope as its own piece of work. | Medium |
| SEC5 | **Add session idle-expiry** | Connect/read rate-limiting shipped 2026-07-09 (IP-keyed, fails open if Redis is down). Remaining: a leaked/idle session_id never expires. Note: the "24h inactivity auto-close" precedent originally cited here is dead code — `_run_auto_close`/`_run_auto_resolve_visitor_ended` in `auto_close_scheduler.py` are never registered with the live APScheduler instance (only two unrelated notification jobs are). Building this means designing fresh expiry semantics, not reviving an existing job — natural to pair with SEC3 since both touch "what makes a session still valid." | Low |
| SEC6 | **Fix silent-skip session checks + unauthenticated rating read** | Surfaced while investigating SEC1-5, not yet fixed. `POST /ratings/submit` and the forms-submission route (`backend/app/api/forms.py`) only cross-check `session_id` against the conversation *if the field is supplied at all* — omitting it skips the check entirely, worse than blind trust. Separately, `GET /widget/conversations/{conversation_id}/rating` (`widget.py`) has no session_id/website check whatsoever — any conversation's rating is readable by ID alone. | Medium |
| SEC7 | **Stop exposing sequential Organization/Website IDs to customers** | `OrgSettings.tsx` and the Website Installation tab both display the raw integer `id` ("Org ID: 1", "Website ID: 1") to any Owner/Manager. Investigated whether this is exploitable like the earlier session_id issue — it isn't: `organization_id` is always derived server-side from the authenticated user's own session for regular endpoints, the one endpoint that accepts a client-supplied `org_id` (`/admin/organizations/{org_id}`) is already gated `SYSTEM_MANAGER`-only, and `website_id` is already fully public by design (embedded in every widget WS URL, visible via devtools on any customer site) with the real secret (`widget_key`, already a proper `secrets.token_hex(32)`) doing the actual access control. So this is **not** an access-control bug, just a business-info leak — a competitor watching the counter tick up learns roughly how many customers/sites you have. **Do not migrate the integer primary key to a UUID** — `organizations.id`/`websites.id` are foreign-keyed from nearly every table (users, conversations, teams, tags, ratings, page views, agent assignments...) plus every API response shape and frontend type; that's a large, genuinely risky migration for a cosmetic concern. Instead reuse the pattern already proven in this codebase: `Conversation.short_id` (`backend/app/models/conversation.py`) is exactly this — a separate random display identifier alongside the untouched integer PK used internally for joins. Add the same `short_id` column to `Organization`/`Website`, backfill existing rows with a one-time script, swap the two display spots to show it instead of `.id`. Purely additive — no FK changes, no cascade, nothing touching conversations/routing/the widget. | Low |

## Super Admin

| # | Title | Description | Priority |
|---|-------|-------------|----------|
| SA1 | **Flesh out the Super Admin (platform) dashboard** | `SuperAdminHome.tsx` is still a stub ("Organization management pages will live under /superadmin/*"), and `SuperAdminStats`/`SuperAdminOrgs` only show raw counts and a bare org list — no drill-down actions beyond org detail. Needs the operational features a platform admin actually reaches for: org lifecycle actions (suspend/reactivate/verify from the list, not just view), plan/billing visibility, system health (WS connection counts, queue/job status, error rates), recent-signups/activity feed, and impersonation or support-login for debugging a tenant's issue. Scope out which of these are must-have vs. nice-to-have before building. | Medium |
| SA2 | **Backup & Restore (Super Admin)** | No backup/restore mechanism exists today. Scope: (1) **What** — Postgres DB via `pg_dump` (logical/portable format, not physical/WAL — those don't survive a differing target host) *and* uploaded attachments on disk (`UPLOADS_DIR`), since attachments aren't stored in the DB at all and a DB-only backup would "restore" with every attachment broken. (2) **Where** — v1 ships to local disk (simplest, no new infra/credentials to stand up first); S3-compatible offsite storage is the deliberate fast-follow before this is trusted for real disaster recovery, since local-only means a disk failure takes out backup and live data together — track that follow-up explicitly, don't let "v1 shipped" quietly become "done." (3) **Restore scope — deliberately narrow for v1**: "download a backup + documented procedure to restore into a separate/fresh instance," not a one-click in-app restore against the currently-running database — that single button would silently overwrite every tenant's current data platform-wide with no undo, and is a much bigger, separately-scoped ask if wanted later (also implies the app holding/accepting credentials to arbitrary external DB targets, its own risk surface). (4) **Access** — SYSTEM_MANAGER-only, same gate as existing `/admin/*` routes; backup files contain full PII for every tenant (names, emails, phones, conversation content, password hashes) so should be encrypted at rest. (5) **Trigger** — scheduled (reuse the app's existing `AsyncIOScheduler` in `auto_close_scheduler.py`, already running notification jobs — don't stand up a second scheduler) plus an on-demand "back up now" action, with old backups auto-expired so storage doesn't grow unbounded. (6) **UI** — a "Backups" view in the Super Admin dashboard listing generated backups (timestamp, size, download link); natural to build alongside SA1 rather than as a separate surface. | Medium |
